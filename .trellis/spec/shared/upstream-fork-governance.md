# 上游跟踪与分叉治理

## 适用条件与边界

- 仓库持续跟踪外部上游，同时保留本地、组织内或私有差异时，使用本规范管理这些偏离。
- 本规范只拥有跨项目的偏离治理合同。具体上游地址、分支策略、差异清单格式、私有功能、发布和部署要求由项目规则管理。
- 没有上游关系的原创项目，或不会长期保留的一次性实验，不为套用流程而建立分叉台账；实验一旦进入长期维护范围，就按本规范补齐记录。

## 上游优先的决策顺序

1. 明确当前上游基线、目标行为和本地偏离，再检查上游当前实现、发布说明以及相关 issue 或 PR；历史印象不能代替当前证据。
2. 上游已经满足要求时，优先按项目 Git 合同同步并验证上游实现，不继续维护等价的本地补丁。
3. 问题具有通用性时，先评估能否在上游修复；提交 issue、PR 或其它外部动作仍遵循当前项目的授权规则。
4. 只有上游尚未解决、无法按当前时限采用，或需求本来只属于本地时，才保留偏离，并记录选择本地方案的原因。

## 偏离记录与实现约束

每项长期偏离都应有稳定记录，至少回答：

| 字段 | 必须说明的内容 |
|---|---|
| 目的与范围 | 解决什么需求，影响哪些入口，不包含哪些范围 |
| 来源关系 | 基于哪个可识别的上游版本或提交，是否有相关 issue、PR 或发布 |
| 实现位置 | 代码、配置或适配层的项目相对入口，以及如何识别这项偏离 |
| 验证 | 覆盖该偏离和上游兼容性的测试、检查或人工验收 |
| 风险 | 安全、兼容、升级和维护影响 |
| 移除条件 | 哪个上游能力、需求变化或验证结果出现后可以删除 |

- 偏离保持最小、独立且可撤销；优先使用明确的配置或窄适配层，不无故重写上游大段实现。
- 不把多个无关私人需求合成一个补丁，也不以生成物或构建输出作为唯一实现位置。
- 记录遵循敏感信息规则：共享说明和可提交台账使用占位符、相对入口和公开标识，凭据与机器私有事实留在受保护的项目位置。

## 上游同步与审查

- 同步前固定待同步的上游身份，检查工作区和当前偏离清单，并确认每项偏离都能从实现位置和验证入口追溯。
- 上游同步、冲突处理和项目偏离按可独立审查的逻辑单元组织；若创建提交，不把纯上游同步与新增或改写的项目偏离混入同一提交。
- 同步后逐项判断偏离是仍需保留、需要调整还是已经可移除；同时检查是否出现未记录的新差异、遗漏补丁或被意外恢复的旧实现。
- 分别验证上游基线行为和仍保留的项目差异。不能因为上游测试通过，就推断私人入口、配置或集成仍然有效。
- 上游身份不明确、偏离来源无法解释、冲突未解决或验证失败时，对当前同步失败关闭；保留可恢复现场并报告，不用强制覆盖制造收敛。

## 能力生命周期与预览证据

- `project-required` 表示能力只属于项目合同；`profile-overlay` 表示当前稳定上游仍需窄适配；`upstream-supported` 表示固定稳定版本已原生提供；`candidate-removal` 表示只进入删除候选；`deferred` 表示当前明确不推进。
- 判断必须基于固定稳定版本的可重现 fixture。beta、preview 或未固定的分支只能形成预览记录，不能把能力推进到 `upstream-supported`，也不能据此删除稳定 profile overlay。
- 删除候选至少同时具备 fixture、profile 回归测试和一个真实消费者 pilot 三类成功证据；任一缺失都失败关闭并继续保留偏离。
- 上游 review 默认复用已有 fixture，不应因只读审查隐式下载或运行不受限的网络命令。需要生成 fixture 时必须显式请求，并设置超时与清理边界。

## 移除与退役

- 上游已经提供等价能力、需求取消、偏离不再被调用或维护风险超过收益时，立即评估移除条件，而不是默认永久携带。
- 移除前用原偏离的验收入口证明上游或新基线满足需求，并检查配置、数据、调用方和部署面是否仍有依赖。
- 上游已经提供等价能力时，默认方案是删除个人补丁、专用于该补丁的测试与配置覆盖，再直接采用和验证上游实现；不得并行保留两套等价实现。只有上游行为仍缺少已记录的项目合同，才继续保留最小偏离。
- 在独立、可回退的变更中删除偏离及其专用配置和过期说明；原测试若只证明已删除补丁的内部实现，应一并删除，仍能约束项目需求或上游回归的测试则调整为面向行为的验收。
- 更新偏离清单和上游关系，明确实际移除与尚待处理的部分。代码删除、发布或部署是否发生，仍按项目事实分别报告。
