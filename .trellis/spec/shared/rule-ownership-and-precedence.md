# 规则归属与优先级

## 一条规则只保留一个完整事实源

- 入口文件只负责说明身份、优先级、硬边界和路由；详细合同写入最匹配的 spec 或专题文档。
- 同一规则不要在 `AGENTS.md`、多个 spec 和 README 中全文复制。其它入口使用链接和一句适用说明。
- 修改规则前先搜索同义条目。已有事实源时合并或修订，不在文件末尾追加第二个版本。
- 新规则应融入事实源中最匹配的现有章节，并保持文档的逻辑结构。新增内容会形成第二个完整主题或大段尾部补丁时，先重排、合并或拆分文档，不按日期把整段追加到末尾。
- 模板、生成投影或同步副本作为派生内容时，必须能追溯到一个事实源及其更新方式。修改事实源后同步或重新生成，并检查没有漂移。
- 在不损失约束的前提下，规则正文用尽量少的文字写清触发条件、必做或禁止动作和验证方式；理由与例子只保留到足以避免误用。

## 共享与项目规则的边界

- 共享规范只保存跨多个仓库成立的最低底线。
- 项目规则保存业务事实、技术合同、目录结构、命令、数值、分支、部署和验收细节。
- 项目可以加强共享底线；需要降低或改变时，必须明确记录触发条件、理由、影响范围和替代验收。
- 用户当前明确要求高于既有规范。新要求取代旧规则时，应在同一轮修正当前入口，不能长期保留互相矛盾的版本。

## 新规则进入共享仓库的门槛

同时满足以下条件才可提升为共享规则：

- 已在多个仓库重复出现，或其性质显然与具体项目无关。
- 经过验证或得到用户明确确认，不是讨论中的候选方案。
- Mac/Windows 及不同 AI 客户端都能理解，不依赖单机绝对路径或私有工具状态。
- 能写清触发条件、必做动作、禁止动作和验证结果。
- 不与 Trellis 官方模板、工作流或平台配置重复竞争所有权。

一次性要求、临时状态、未验证猜测、历史叙事和敏感信息不得提升为共享规则。

## 重构与删除

1. 先列出旧入口、标题和链接，建立“旧位置 → 新位置”映射。
2. 每条有效规则有新归属后，才能删除旧副本。
3. 冲突规则按当前用户要求、项目事实和可执行证据解决。
4. 更新索引和引用，运行链接检查与定向搜索。
5. 不回写历史任务或 Git 历史来制造表面一致。
