# 长期知识沉淀

## 什么时候应沉淀

用户明确提出并会持续影响后续工作的原则、设计意图、约束、验收口径或稳定偏好，应在本轮结束前评估并写入长期事实源，不只留在聊天里。

一轮工作没有产生新的、稳定且可复用的知识时，不需要为了完成流程而修改规范；保留现有事实源即可。

以下内容不沉淀：

- 一次性安排、当前进度和临时绕行。
- 讨论中的备选方案或未经验证的猜测。
- 用户明确要求“只讨论”“暂时不改”或“不记录”的内容。
- 密钥、账号、机器路径和其它敏感或单机事实。

## 写入步骤

1. 确认含义、适用范围和稳定性。
2. 搜索现有规则，更新拥有者而不是创建重复条目。
3. 在不改变原意的前提下去除口语、会话背景和临时日期，改写为可执行规则。
4. 如果润色会扩大范围、与当前规则冲突或涉及高风险权限，先向用户说明差异。
5. 写入后更新必要索引，并在最终汇报中说明落点和核心变化。

## 路由

| 内容 | 推荐事实源 |
|---|---|
| 项目身份、入口、协作方式和硬边界 | 项目 `AGENTS.md` |
| 多项目都成立的协作与质量底线 | `.trellis/spec/shared/**` |
| 项目业务、API、数据、测试和部署合同 | 项目自己的 `.trellis/spec/**` |
| 专题事实、操作步骤和证据 | 对应 `docs/**` 或领域文档 |
| 当前任务决策、一次性证据和进度 | `.trellis/tasks/**` 或 `.trellis/workspace/**` |
| 用户级客户端、账号和机器状态 | 用户级或 ignored 本地配置，不进项目 Git |

同一规则只完整维护一次，其它位置链接到事实源。
